# MCP tools and local operation

Implemented on Jen against Nora's `001_init.sql` (merged into dev as `97406cb`).
The server uses the official Python MCP SDK, pinned to 1.30.0, with stateless
Streamable HTTP and JSON responses at `/mcp`. No database writes, migrations,
live web fetches, LLM calls, or deployments happen when invoking these tools.

## Store contract

`database/migrations/001_init.sql` is authoritative; parts of the older project
notes describe numeric categories and a store still awaiting commit and are stale.

- `categories.name` is a text primary key. Seed names are `Sales Methodology and
  Process`, `Segmentation and Territory`, and `Enablement Operations`. The store
  can support additional names; the three category tools target the seeded names.
- `scrape_log` audits attempted URLs. It is not retrieval content, has no document
  foreign key, and can include failures without documents.
- `documents` represents public pages or internal files, with a category, access
  labels, metadata, and at least a URL or a source filename. It has no body text.
- `chunks` references a document with cascading deletion. It stores the source text,
  text section ID (`doc_id:section:n`), section/chunk indexes, heading hierarchy,
  confidence tags, labels, and character offsets into the original section.
- `units` references a chunk with cascading deletion. Only `know_how` and `knowledge`
  are stored; supported types are `how_to`, `definition`, `statistic`, and `example`.
  Context is JSON (`who`, `industry`, `company_size`, `situation`); outcomes and
  dates can be absent. The unit's `section_id` is an integer section index, unlike
  the chunk's text section ID. Source URL/domain may be null for internal files.
- Embeddings are nullable `vector(384)`, generated by normalized
  `all-MiniLM-L6-v2`. Query embedding uses the same shared `embed.embed_texts`.
  A different model requires re-embedding and the appropriate migration, even
  when its dimension is also 384. Semantic chunk-boundary embeddings are separate.
- `served_units` joins all three content tables. Effective visibility is public
  only if the unit is external, both parents are public, and all three
  sensitivities are public. Otherwise visibility is internal. Effective sensitivity
  is the strictest of the three (`confidential` > `internal` > `public`).

Search reads `served_units`, excludes null embeddings, applies filters first, then
orders by exact cosine distance (`<=>`), with unit ID as a stable tie-breaker.
There is no approximate index or relevance threshold. Nearest results are
candidates, not guaranteed relevant answers. Distance is not a confidence score.
`get_source` joins the view to `chunks` for supporting passages and does not
require an embedding. It does not return unprocessed documents with no served units.
Raw vectors, database URLs, and unrelated database fields are not returned.

## Serving policy

The Nov 14 decision in `CLAUDE.md` permits serving public and internal units without
login. This implementation follows it. Visibility/sensitivity and confidence tags
are retained in responses. This is deployment-wide policy, not per-user access
control. Set `MCP_ALLOWED_VISIBILITY=public` to narrow the entire endpoint; callers
cannot override it. Invalid policy values fail startup and retrieval.

Do not commit internal content, credentials, or logs containing source passages.
The MCP host-header allowlist protects against DNS rebinding; it is not authentication.

## Tools

| Tool | Required inputs | Optional inputs | Behavior |
|---|---|---|---|
| `get_sales_methodology` | `query` | `entity`, `topic`, `role`, `industry`, `company_size`, `limit=5` | Methodology/process category search |
| `get_segmentation_guidance` | `query` | Same filters | Segmentation/territory category search |
| `get_enablement_practices` | `query` | Same filters | Enablement category search |
| `get_source` | `identifier` | `identifier_type="unit_id"`, `limit=5` | Exact stored lookup; types: `unit_id`, `chunk_id`, `doc_id`, `url` |
| `get_objection_handling` | `objection` | `entity`, `company_size`, `limit=5` | Cross-category candidate objection guidance |
| `compare_approaches` | `approaches` (2–4 distinct names), `question` | `limit_per_approach=3` | Separate entity-filtered evidence for each approach; no winner inferred |
| `map_value_drivers` | `customer_context`, `offering` | `limit=5` | Candidate source claims with their context, reported outcome, citation, and `requires_review` applicability |
| `audit_messaging_alignment` | `message`, `reference_query` | `limit=5` | Retrieve reference evidence and show shared words for review; no semantic verdict |
| `score_adherence_metric` | `content`, `criteria` (1–20 distinct literal phrases) | None | Equal-weight phrase coverage score with auditable source-text matches; no DB required |

All result limits must be integers from 1 to 20. Empty strings and excessive input
lengths are rejected. Topic filters match `topic`; entity filters match topic,
claim, or heading. Matching is case insensitive, with LIKE wildcards escaped.
MEDDIC and MEDDICC are aliases. Context filters map role to `context.who`, industry
to `context.industry`, and company_size to `context.company_size`; they do not infer
missing metadata or translate segment thresholds. Filters may reduce recall.

Retrieval responses have `status` (`ok` or `no_results`), `results`, a useful
`message`, and an evidence caveat. Each result includes the claim, level/type,
context, outcome, tags, effective labels, cosine distance when searched, and a
citation (unit/chunk/document IDs, URL or file/title, publisher/date, heading/path,
evidence quote, and unit offsets). Offsets refer to `section.text`, not necessarily
to an exact quote span. `get_source` separately returns actual parent chunk text
and chunk offsets. Source lookup is bounded and can return multiple units from a
chunk; it is not full-document pagination. No-result messages can also mean missing
embeddings, active filters, or an unpopulated store. Operational failures become
sanitized MCP tool errors rather than fabricated answers.

Comparison returns `insufficient_evidence` if any approach has no results.
Value-driver mappings are candidates and never invent product capabilities or ROI.
Audit uses case-insensitive word overlap (with a small stop-word list); overlaps do
not establish semantic agreement or detect contradictions.

Scoring formula: `100 * matched phrases / supplied phrases`, rounded to two decimals.
Matches ignore case and collapse whitespace, require word boundaries, and return
exact excerpts and offsets into the stripped input content. Negated statements can
match. This is explicitly an `explicit_phrase_coverage` metric, **not** a validated
sales adherence, semantic, effectiveness, or compliance score. A sponsor-approved
rubric and semantic scoring contract would be a separate extension.

## Run locally

From the repository root, using the existing virtual environment:

```bash
.venv/bin/python -m pip install -r requirements.txt
# Set DATABASE_URL in exported variables or gitignored .env.
.venv/bin/python -m mcp_server.server
```

Connect an MCP client using Streamable HTTP to `http://127.0.0.1:8000/mcp`.
The database must already have migration 001 and loaded units. Startup/tool listing
and phrase scoring do not connect to Postgres or download the embedding model.
The first vector query downloads MiniLM if it is not cached (`HF_HOME` can select
a prepared cache). Model loading and DB work run outside the HTTP event loop.
Shared model loading/inference is serialized to avoid concurrent cold starts.

Environment variables:

- `DATABASE_URL`: existing store connection; never printed.
- `EMBED_MODEL`: must be `all-MiniLM-L6-v2` for this migration.
- `MCP_HOST`: bind address, default `127.0.0.1`.
- `PORT`: default `8000`; host platforms may supply it.
- `MCP_ALLOWED_HOSTS`: comma-separated host headers; defaults to localhost/loopback.
- `MCP_ALLOWED_VISIBILITY`: defaults to `public,internal` per client decision.

For a future hosted launch, bind `MCP_HOST=0.0.0.0`, allow the actual deployment
hostname in `MCP_ALLOWED_HOSTS`, configure `DATABASE_URL`, and provide enough RAM
for the model. A suitable launch command is `python -m mcp_server.server`.
These instructions do not deploy anything or modify the existing deployment scaffold.
Use a database role with SELECT access for the running retrieval service.

Examples of MCP tool arguments:

```json
{"query":"How should we qualify an enterprise opportunity?","entity":"MEDDICC","limit":3}
```

```json
{"identifier":"<unit_id returned by search>","identifier_type":"unit_id"}
```

```json
{"approaches":["MEDDICC","BANT"],"question":"How do they address qualification?"}
```

```json
{"content":"Ask the buyer about budget and timeline.","criteria":["budget","timeline","economic buyer"]}
```

The final example returns `score: 66.67`, `matched: 2`, `total: 3`, with the
matching excerpts; it says nothing about the overall quality of the sales process.

## Verification and remaining limits

Run `.venv/bin/python -m pytest tests`. New tests use synthetic records, fake
embeddings and mocked database cursors; the HTTP test exercises actual MCP
initialization, discovery, and invocation via ASGI. No shared database is modified.
Live pgvector execution, real-model retrieval relevance, corpus coverage, memory
fit on the selected host, and Salesforce-client connectivity require environment
validation. Existing live database/uploader tests require a disposable local DB.
